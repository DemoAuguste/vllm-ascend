# Qwen3.8-27B 量化存储与位宽分配分析

> 数据来源：`/opt/zh/slq-official`（SLQ 官方流水线，2026-10-18/19）
> 统计脚本：`stat_slq27b.py`（本目录外的服务器副本），`error_db.json` 的 `param_counts` 为准
> 口径说明：**bpp = 参数加权平均位宽（含 g128 的 scale/zero 开销）**；体积按十进制 GB（1 GB = 10⁹ B）

---

## 1. 结论速览

| 配置 | 平均位宽（含开销） | 估算部署体积* | 相对 BF16 压缩比 | 500 样本 zero-shot 恢复 |
|------|------------------|--------------|-----------------|------------------------|
| BF16 | 16.000 | 54.71 GB | 1.00× | 100% |
| uniform-4 | 4.156 | 18.95 GB | 2.89× | 100.7%（200 样本） |
| **b4.0** | **4.000** | 18.47 GB | 2.96× | — |
| **b3.8** | **3.800** | 17.87 GB | 3.06× | **101.6%** |
| **b3.6（推荐）** | **3.600** | **17.26 GB** | **3.17×** | **100.0%** |
| b3.4 | 3.400 | 16.65 GB | 3.29× | 99.45%（200 样本） |

\* 估算口径：量化权重按 nominal bits 打包 + g128 的 scale/zero（bf16+bf16，+0.25 bpp）+ 未量化参数按 BF16。
若按论文计费口径（scale bf16 + zero int4，+0.156 bpp），b3.6 为 **16.97 GB / 3.22×**。

> **注意**：当前交付的 `ckpt_27b/b36|b38` 是 **fake-quant（BF16 权重落在整数格点）**，实测 **54.74 GB，与 BF16 基本相同**。上表的 17 GB 是**真正 INT 打包后**的体积，需要打包 kernel / 量化加载路径才能落地。

## 2. 实测体积

| 产物 | 字节数 | 换算 | 说明 |
|------|--------|------|------|
| 原始 BF16 模型目录 | 55,586,114,863 | 55.59 GB / 51.77 GiB | 含 config/tokenizer 等非权重文件 |
| 原始 BF16 权重（index `total_size`） | 55,562,855,904 | 55.56 GB | 27.78B 参数 @ 2 B |
| **fake-quant checkpoint（b36/b38）** | **54,743,827,250** | **54.74 GB / 50.98 GiB** | 27.36B 参数 @ 2 B，**无存储收益** |
| 量化层权重库（存储中间件，4 档位 × 496 层，反量化 BF16） | 295,261,412,807 | 295.26 GB | 仅训练/搜索期使用，不随部署分发 |

- checkpoint 比原模型小 **0.85 GB（1.5%）**，来源于重新序列化时的共享张量/文件组织差异，不是量化收益。
- 结论：**fake-quant 只改数值、不改体积**；体积收益必须在打包格式（INT4/INT2 位打包）下才体现。

## 3. 混合精度位宽分布

量化层共 **496 个 Linear**，合计 **24.35B 参数**（占模型 27.36B 的 89.0%）；其余 3.01B（embedding、lm_head、norm、conv1d、visual tower 等）保持 BF16。

### 3.1 按层数 / 参数量的占比

| 配置 | 2-bit | 4-bit | 6-bit | 8-bit | 平均位宽（nominal） |
|------|-------|-------|-------|-------|---------------------|
| **b3.6（推荐）** | 148 层 / **29.84%**<br>6.78B 参数 / **27.85%** | 312 层 / **62.90%**<br>17.56B / **72.11%** | 23 层 / 4.64%<br>5.65M / 0.02% | 13 层 / 2.62%<br>3.19M / 0.01% | **3.444** |
| b3.8 | 103 / 20.77%<br>4.35B / 17.86% | 354 / 71.37%<br>19.99B / 82.10% | 22 / 4.44%<br>5.41M / 0.02% | 17 / 3.43%<br>4.18M / 0.02% | 3.644 |
| b3.4 | 183 / 36.90%<br>9.21B / 37.84% | 281 / 56.65%<br>15.13B / 62.13% | 24 / 4.84%<br>5.90M / 0.02% | 8 / 1.61%<br>1.97M / 0.01% | 3.244 |
| b4.0 | 52 / 10.48%<br>1.93B / 7.92% | 379 / 76.41%<br>22.41B / 92.02% | 15 / 3.02%<br>3.69M / 0.02% | 50 / 10.08%<br>12.29M / 0.05% | 3.844 |

**关键观察**：

1. **6/8-bit 层数量看着不少（合计 7%–13%），但参数量占比只有 0.03%–0.07%**——被抬高位宽的全是 `linear_attn.in_proj_a / in_proj_b` 这类极小的门控投影（每个仅约 0.18M 参数）。
2. 参数主体被压到 **2-bit + 4-bit**：b3.6 中 99.96% 的参数落在 2/4-bit。
3. 若按"层数"看平均会高估位宽（b3.6 层均 3.60 vs 参数加权 3.44），**bpp 必须以参数量加权**。

### 3.2 按模块类型的平均位宽（参数加权，nominal bit）

| 模块 | 参数量 | b3.6 | b3.8 | 说明 |
|------|--------|------|------|------|
| `mlp.down_proj` | 5.70B | 3.625 | 3.750 | 4-bit 主体，少数块降 2-bit |
| `mlp.gate_proj` | 5.70B | **3.438** | 3.625 | 与 `up_proj` 同组共享位宽 |
| `mlp.up_proj` | 5.70B | **3.438** | 3.625 | |
| `linear_attn.in_proj_qkv` | 2.52B | **3.125** | 3.708 | 最大的单个投影，最激进 |
| `linear_attn.in_proj_z` | 1.51B | **2.875** | 3.458 | 全模型最低位宽档 |
| `linear_attn.out_proj` | 1.51B | 3.750 | 3.917 | |
| `self_attn.q_proj` | 1.01B | 3.500 | 3.875 | |
| `self_attn.o_proj` | 0.50B | 3.750 | 3.875 | |
| `self_attn.k_proj` | 0.08B | 3.500 | 3.875 | |
| `self_attn.v_proj` | 0.08B | 3.500 | 3.875 | |
| `linear_attn.in_proj_b` | 0.012B | **4.583** | 4.750 | 极小但最敏感，被保护到 4/6-bit |
| `linear_attn.in_proj_a` | 0.012B | 4.125 | 4.375 | 同上 |

**规律**：

- **`in_proj_a / in_proj_b`（线性注意力的门控标量投影）最敏感**，尽管只有 0.024B 参数，ILP 仍优先给它们高位宽——代价几乎为零（参数太少），收益是避免门控失真放大。
- **`in_proj_z / in_proj_qkv` 最不敏感**，承载了最多 2-bit 降位，这是 b3.6 能做到 3.6 bpp 的主要来源。
- MLP 三个投影（gate/up/down）位宽接近，`gate+up` 因同组约束完全一致。
- 与 SLQ 论文"K/V 更敏感、MLP 更不敏感"的结论在 hybrid 架构上表现为：**线性注意力的小门控投影 > full-attention 的 q/k/v > MLP**。

## 4. 存储换算明细

量化参数 **Q = 24,350,556,160**；未量化参数 **U = 3,006,172,400**（BF16）。

```
量化权重字节 = Q × nominal_bits / 8
量化开销字节 = Q × overhead_bpp / 8      # 当前导出格式 overhead = 0.25（scale bf16 + zero bf16，g128）
未量化权重   = U × 2
```

| 配置 | 量化权重 | 量化开销 | 未量化部分 | 合计 | vs BF16(54.71 GB) |
|------|---------|---------|-----------|------|-------------------|
| b3.4 | 9.87 GB | 0.76 GB | 6.01 GB | **16.65 GB** | 3.29× |
| **b3.6** | 10.48 GB | 0.76 GB | 6.01 GB | **17.26 GB** | **3.17×** |
| b3.8 | 11.09 GB | 0.76 GB | 6.01 GB | **17.87 GB** | 3.06× |
| b4.0 | 11.70 GB | 0.76 GB | 6.01 GB | **18.47 GB** | 2.96× |
| uniform-4 | 12.18 GB | 0.76 GB | 6.01 GB | **18.95 GB** | 2.89× |

- 若 zero 以 int4 打包（论文/推理 kernel 口径，overhead 0.156 bpp），各配置再省 **0.28 GB**：b3.6 → **16.97 GB（3.22×）**。
- **未量化部分占 6.01 GB（35%）**，是压缩比的主要天花板；若要进一步压，需要对 embedding / lm_head 做单独处理（如 8-bit 或共享）。
- 当前官方层库每个层目录同时保存 `2/4/6/8.pth`（反量化 BF16）和对应 `*_qparams.pt`，所以 295 GB 是"4 套全量权重"的中间态，不是部署体积。

### 4.1 qparams 实测格式

以 `layers.0.mlp.gate_proj/4_qparams.pt` 为例（17408×5120，g128）：

| 字段 | 形状 | dtype | 字节数 |
|------|------|-------|--------|
| `qweight` | (17408, 5120) | uint8 | 89,128,960 |
| `scales` | (17408, 40) | bfloat16 | 1,392,640 |
| `zeros` | (17408, 40) | bfloat16 | 1,392,640 |

- `qweight` 为 **uint8 容器、一元素存一个整数索引**（非位打包）；真正打包后 4-bit 可减半。
- scale/zero 各 16 bit / 128 参数 → 合计 **0.25 bpp**；这与论文 +0.156 的差异仅在 zero 的存储方式。

## 5. 对部署的影响

| 项目 | 现状（fake-quant BF16） | 真正 INT 打包后（预期） |
|------|------------------------|------------------------|
| 每卡权重（TP=2，27B） | **25.61 GiB**（实测） | ≈ **8.1 GiB**（17.26 GB ÷ 2） |
| KV cache（剩余显存） | **23.99 GiB / 326K tokens** | 约 **41 GiB / 560K tokens**（同卡同利用率） |
| 引擎初始化 | 216 s | 需额外反量化/打包加载，预计相近或略慢 |
| 吞吐 | 4.9 tok/s（eager、xhigh reasoning、共享卡） | 取决于 INT kernel，通常优于 BF16 反量化路径 |

> 当前 TP=2 部署 PASS 用的是 fake-quant 权重，vLLM 识别为 float 加载，**显存收益尚未体现**；要拿到 3.17× 的显存/体积收益，需要 `--quant-format humming_online`（官方 Humming 路径）或自行实现 INT 打包加载。

## 6. 复现命令

```bash
# 生成 b3.6/b3.8 配置（ILP，给定平均位宽预算）
python make_configs.py

# 拼装 fake checkpoint
python slq_build_checkpoint.py \
  --model <Qwen3.8-27B> \
  --layer-dir .../data/slq_27b/<snap>/4bit \
  --config config_tl27b_b3.6.txt \
  --output-dir ckpt_27b --subdir-name b36 \
  --dtype bfloat16 --quant-format fake --group-size 128 --force

# 双卡部署（spawn 模式，需补齐 VLM preprocessor 文件）
bash run_deploy27b.sh <ckpt>/b36 2 5,7 1 8100
```
